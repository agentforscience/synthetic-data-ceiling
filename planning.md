## Motivation & Novelty Assessment

### Why This Research Matters
Model-generated data is now the default way to stretch a small real dataset (distillation, augmentation,
instruction tuning). Practitioners must choose *how much* to generate, and the cost is linear in that
choice. If benefit saturates early, most generation budgets are wasted; if large ratios actively hurt,
they are harmful. A measured dose–response curve per task family is directly actionable.

### Gap in Existing Work
(From my own knowledge of the literature; no review file was supplied.)
- *Model-collapse* work (Shumailov et al. 2023/2024; Alemohammad et al. 2023 "MAD"; Dohmatob et al. 2024;
  Gerstgrasser et al. 2024; Bertrand et al. 2024) studies **recursive, multi-generation** self-training,
  and mostly reports perplexity or image quality. It says little about the **single-generation**
  augmentation setting people actually use, with a stronger teacher and a fixed real set.
- *Synthetic augmentation* work (He et al. 2022; Azizi et al. 2023; Fan et al. 2023 for images; ZeroGen,
  Yu et al. 2023, Li et al. 2023 for text classification) reports scaling curves for one task family at a
  time, with different generators, students, and metrics, so cross-domain comparisons are not possible.
- Nobody (to my knowledge) has run one protocol — same teacher, same student, same real-set size, same
  ratio grid — across code, reasoning, and creative generation, with a **real-data scaling control**
  and a direct **measurement of generator diversity saturation** as the proposed mechanism.

### Our Novel Contribution
A controlled dose–response study of the synthetic:real ratio (0 → 50:1) across three task families with a
shared protocol, explicit tests of the functional form (log vs. saturating vs. power-law), the "80% at
3:1" claim, the ">10:1 plateau/degradation" claim, and the cross-domain ordering, plus a mechanism check
(does effective sample diversity of the synthetic pool saturate?).

### Experiment Justification
- **E1 – Ratio sweep (core).** Fine-tune the student on 100 real + r·100 synthetic examples for each r in
  the grid, 3 tasks, 3 seeds. Gives the dose–response curve everything else depends on.
- **E2 – Real-data scaling control.** Same total sizes but all-real data. Without it a plateau cannot be
  attributed to *synthetic* data (it could just be student capacity / data saturation).
- **E3 – Pool diversity vs. pool size.** Tests the hypothesised mechanism (mode collapse): duplicates,
  distinct n-grams, embedding-space effective sample size of synthetic vs. real sets of equal size.
- **E4 – Zero-shot student baseline.** Anchors the scale: how much does any fine-tuning buy?
- **E5 (if time) – Ablations.** Unfiltered code synthetic data (removes the execution-verification
  advantage code enjoys), and a judge/quality view of creative outputs.

## Research Question
When a fixed real training set is augmented with data generated by a stronger model, how does held-out
performance on real data change with the synthetic:real ratio r, and does this differ between code
generation, mathematical reasoning, and creative writing?

## Hypothesis Decomposition
- **H1a (shape):** gain(r) is better described by a·ln(1+r) than by linear, power-law, or bounded
  saturating forms.
- **H1b (80% @ 3:1):** [perf(3) − perf(0)] / [max_r perf(r) − perf(0)] ≥ 0.8.
- **H2a (plateau/degrade >10:1):** perf(50) ≤ perf(10) (within noise or lower); slope of perf on ln r for
  r ≥ 10 is ≤ 0.
- **H2b (mechanism):** the synthetic pool's diversity saturates (rising duplicate / near-duplicate rate,
  sub-linear distinct n-gram growth relative to real data) and this tracks the plateau.
- **H3 (ordering):** code is most resilient (latest peak, smallest drop at high r); creative degrades
  earliest (earliest peak / largest drop).

Independent variables: ratio r ∈ {0, 0.5, 1, 2, 3, 5, 10, 20, 50}; task ∈ {code, math, creative};
data source ∈ {synthetic, real control}. Dependent variables below.

## Proposed Methodology

### Approach
Teacher → synthetic pool → student fine-tuning → evaluation on **real** held-out data.
- **Teacher/generator:** `Qwen/Qwen2.5-7B-Instruct` (vLLM, T=1.0, top-p=0.95). Each generation request
  shows 3 random examples from that seed's 100 real examples and asks for one new example. The generator
  therefore only "knows" the task through the real seed set — the realistic augmentation setting.
- **Student:** `Qwen/Qwen2.5-0.5B-Instruct`, full fine-tuning (fp32 weights, bf16 autocast), AdamW,
  lr 2e-5, batch 16, 10% warm-up + cosine. Steps = max(3 epochs, 100 steps). Validation loss on a small
  **real** validation set is evaluated 8 times; the best checkpoint is used for testing (early stopping),
  so small-data conditions are not penalised by over- or under-training.
- A 14× teacher/student size gap makes this a distillation-style setting where synthetic data can help.

### Tasks and data
| Domain | Dataset (real) | Real seed set | Val | Test | Task metric |
|---|---|---|---|---|---|
| Code | MBPP (`full`) | 100 of 374 train | 90 (validation split) | 500 (test split) | pass@1, greedy |
| Math | GSM8K | 100 of train | 200 of train | 1319 (test split) | exact-match accuracy, greedy |
| Creative | ROCStories 2018 (human-written, title → 5-sentence story) | 100 of train | 200 | 1000 (NLL) / 500 titles (generation) | human-text perplexity; Fréchet embedding distance; diversity |

A metric common to all three domains: **per-token NLL of the real held-out reference answers**.
Each seed uses a different 100-example real set **and its own independently generated pool**, so seed
variance includes real-set and generator variance. Subsets are nested (r=1 ⊂ r=2 ⊂ …) to reduce noise
along a curve. Synthetic pools are *not* de-duplicated (duplication is part of the phenomenon). Code
samples are kept only if the teacher's solution passes the teacher's own asserts (standard practice;
flagged as an asymmetry and ablated in E5).

### Experimental Steps
1. Build splits; sanity-check formats; zero-shot student baseline (E4).
2. Generate pools (5,000 usable examples per task × seed; more if throughput allows).
3. Pilot one small and one large condition to verify the training/eval pipeline end to end.
4. E1 ratio sweep; E2 real control (GSM8K, ROCStories at all matched sizes; MBPP only to 374 = r≈2.7,
   limited by the dataset).
5. E3 diversity analysis; curve fitting and statistics; figures; report.

### Baselines
Zero-shot student; real-only (r=0); all-real at matched size (upper reference); teacher's own task score
where cheap to obtain.

### Evaluation Metrics
- Code: pass@1 on MBPP test (execution of the 3 hidden asserts; prompt shows the asserts as is standard).
- Math: accuracy of the number after `####`.
- Creative: perplexity of human test stories (primary, standard in the collapse literature); Fréchet
  distance between MiniLM embeddings of student stories and human stories for the same titles;
  distinct-n and mean pairwise embedding similarity of student stories (sampled at T=1).
- Normalised benefit B(r) = [perf(r) − perf(0)] / [max_r perf(r) − perf(0)], per task.

### Statistical Analysis Plan
- Curve fits on gain vs. r (all seed-level points): linear, a·ln(1+r), power law a·r^b, hyperbolic
  a·r/(r+k), exponential saturation a(1−e^(−r/k)); compare with AICc and R².
- H1b: point estimate of B(3) with a bootstrap CI (resampling seeds and test items).
- H2a: paired differences perf(50) − perf(10) and perf(50) − perf(peak) (paired by seed and test item;
  bootstrap CI / McNemar for binary metrics); OLS slope of perf on ln r for r ≥ 10.
- H3: compare tasks on r* (ratio achieving ≥95% of max benefit), B(3), and relative change from r=10 to 50.
- α = 0.05; three task families × a few planned contrasts → Holm correction within each hypothesis.
- With 3 seeds the between-seed CI is coarse; item-level paired tests provide the power, seed-level
  spread is shown in every plot.

## Expected Outcomes
Supports H: concave gains, B(3) ≥ 0.8 in all tasks, flat/negative slope after 10:1, rising duplicate rate,
code flattest at high r and creative turning down first. Refutes H: gains still rising at 50:1 (no
ceiling in range), B(3) well below 0.8, bounded-saturating or power-law clearly better than log, no
diversity saturation, or a different task ordering.

## Timeline and Milestones
Setup+plan 30 min → generation 30–40 min → sweep ~90 min (4 GPUs) → analysis 30 min → report 30 min.
Buffer ≈ 25%. Critical path: generation throughput, then the sweep.

## Potential Challenges
- Disk: `/data` has ~4 GB free → symlinked venv, no checkpoints saved, compressed outputs.
- Small effect vs. noise on MBPP (500 items) → paired item-level tests, nested subsets.
- Early stopping on real-val NLL may not select the best task-metric checkpoint → also log final-step NLL.
- Creative "performance" has no single accepted metric → report several and state which is primary.
- One teacher, one student, one real-set size → external validity limit; stated in the report.

## Success Criteria
A complete ratio × task × seed grid with real controls, statistical tests for each sub-hypothesis, and an
honest verdict (supported / partially / refuted) per sub-hypothesis.

## Deviations from the plan (logged during execution)

All changes below were made **before any fine-tuned result used in the report was produced**; pilot runs
made under earlier settings were deleted and re-run.

1. **Teacher: Qwen2.5-7B-Instruct → Qwen2.5-3B-Instruct.** The four GPUs turned out to be shared with
   several other jobs. In the ~18 GB that was free, the 7B model left <1 GB of KV cache (≈6 concurrent
   sequences, 343 tokens/s → ~5 h for the pools). The 3B model generates ~8× faster in the same memory.
   The teacher is still 6× larger than the student; its own test scores are reported.
2. **Student optimisation: full fine-tuning → LoRA** (rank 32, α 64, all attention and MLP projections,
   17.6 M trainable parameters; lr 1e-4, batch 8, max(2 epochs, 100 steps), 6 validation checks, best
   checkpoint by real-validation loss). Full fine-tuning needed ~13 GB per worker and only one worker
   fitted; LoRA let 4–5 workers run. Pilots showed validation loss bottoming out after ≈1 epoch, so the
   epoch cap went from 3 to 2 and the learning rate from 2e-4 to 1e-4.
3. **Ratio grid: {0, 0.5, 1, 2, 3, 5, 10, 20, 50} → {0, 1, 2, 3, 5, 10, 20, 30}** for all tasks, with 50:1
   as a low-priority extra for math and creative only. The 3B teacher's code passes its own tests only
   ~51% of the time (7B: 77%), so the code pools (≈3,500–3,800 usable examples) cannot support 50:1.
4. **Real-data control sizes:** matched to ratios {1, 3, 10, 30} (math, creative) and {1, 2.74} (code: all
   374 MBPP training problems).
5. **Generation-based evaluation on 500 test items per task** (GSM8K: first 500 of 1,319) with length caps
   of 256/256/96 new tokens, to keep evaluation affordable on contended GPUs. NLL uses 500/1,319/1,000 items.
6. **Format filter:** teacher outputs containing CJK characters (the Qwen teacher occasionally
   code-switches at T=1) are treated as format violations, like any unparseable output.
7. **ROCStories split:** only the train split has titles, so validation/test sets were carved from it.
8. **Unfiltered-code ablation** reduced to ratios {3, 30}. No LLM-judge view of story quality (no API
   key; local judge skipped for time).
